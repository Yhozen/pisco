PISCO

PISCO Imitates Systems, Compiles Originals. It runs x86 titles in WebAssembly, in a browser tab or in Node, by recompiling their code ahead of time and supplying the system they were written for: one recompiler, one package format (pisco build makes a title image from a recipe and your own copy of the title), and several compatibility runtimes. Nothing of a title is in the repository. Windows titles are checked against Wine, screen by screen and call by call.

Source: github.com/Yhozen/pisco · Progress map: what each runtime implements against what titles use · Videos: releases

Changelog

Libraries on the lifted Linux, linked and opened 2026-11-27PR #64

A program's own shared libraries now run on the lifted Linux: one it is linked against, and one it opens itself with dlopen and calls by name. Each is lifted into a module of its own when its code is first met, and prints what it prints on QEMU (fixtures/linux-dyn, on Alpine's musl).

  • Found from the code: a library's code is met in the middle of a run (its constructor, or a call into it), where no auxiliary vector says what it is. The microvm-x64 machine takes the nearest ELF header below the code whose executable segments hold it, and the image as its loader has relocated it.
  • Where it was met is a function: a constructor no symbol names is a function start the lifter is told of.

Still missing: a network, snapshots.

A distribution's program on the lifted Linux: Alpine's busybox 2026-11-27PR #64

The lifted Linux runs Alpine 3.24.4's busybox as Alpine ships it: position-independent and dynamically linked, on musl's loader. Both the loader and the program are lifted when they first run, each into a module of its own, and they print what they print on QEMU.

  • The loader is taken first: the kernel starts it, at the address its auxiliary vector gives (AT_BASE), and the program after it, at its entry point. The microvm-x64 machine rebuilds each as a program at the addresses it was loaded at, applying the loader's relocations to the copy, as the loader would.
  • Functions found by name: the loader calls some of its own functions through pointers it looks up in its symbol table, so the machine passes the lifter every function its dynamic symbols name.
  • The same addresses each time (norandmaps), so the images, and the lift cache, are the same from one run to the next.

Still missing: shared libraries the loader opens beside musl's.

Programs from anywhere, lifted from memory, on the lifted Linux 2026-11-27PR #64

A program met for the first time is now lifted from its image in memory, not from a file the host has to find. At a program's entry point, its stack's auxiliary vector says where its headers are, and its segments are as the kernel loaded them. The microvm-x64 machine rebuilds the ELF from that and hands it to the host, which lifts it, caches it and loads it. A static program can therefore run from the initramfs, the disk or anywhere: /init copies a program to the disk and runs it from there.

  • An image from memory has no symbols, so the lifter now also takes function addresses from immediates (mov $f, %eax, as musl's start does).
  • tests/run.sh kernel checks a program run from the disk.

Still missing: position-independent and dynamically linked programs, which are somewhere else each time.

Programs lifted when they first run, on the lifted Linux 2026-11-27PR #60

A program that no build lifted can now run on the lifted Linux kernel, in Node. When the microvm-x64 machine meets user code it has no lifted program for, it hands the page to the host. The host finds the initramfs program whose code page there is the same, lifts it into a module of its own, caches it by its sha256, loads it, and the machine goes on. /init runs fixtures/linux-proc that way: lifted in 2.7 s the first time, from the cache after, printing what it prints on QEMU.

  • web/lift.mjs (Node) reads the initramfs, compares code pages, and runs tools/build-side.sh (the lifter, wasi-sdk, wasm-ld -shared).
  • A machine's title exports what any lifted program may import (rt/microvm-x64/side-exports.txt), not only what its build's programs import.

Still missing: the page cannot lift (no lifter there), and programs on the disk or written while the machine runs are not found yet.

bash on the lifted Linux, in a module of its own 2026-11-27PR #60

A program can now be a wasm module of its own, loaded by the host beside the kernel's. bash, whose GPL-3.0 licence keeps it out of a module linked with the GPL-2.0-only kernel, runs that way on the lifted Linux: /init prints what it prints on QEMU, in Node and in headless Chrome.

  • A side module: the lifted program compiled position-independent and linked by wasm-ld -shared. It imports the title's memory, table, C stack pointer and the machine's functions.
  • web/side.mjs loads it as a dynamic linker loads a library: its memory taken from the machine, its functions added to the table, its relocations applied, then it is registered with the machine, which finds it by its code pages like any program.
  • pisco build: [lifter] modules makes each one a layer of the image; the title's module exports what they import.
  • LICENSING.md says how a machine's programs are licensed, and what this does and does not settle.

fastfetch and cowsay on the lifted Linux 2026-11-27PR #60

Real programs run on the lifted Linux kernel. fastfetch 2.71.0 and cowsay 3.8.4 on perl 5.44.0 are in its initramfs beside busybox, all static at the same addresses, each lifted on its own into the kernel's module. /init prints fastfetch's lines and cowsay's cow exactly as on QEMU.

  • fastfetch reads the kernel's own /proc and /sys: the machine's CPU (pisco microvm-x64 (lifted) @ 1.00 GHz), its 244 MiB of memory, the root file system's use.
  • tools/build-linux.sh builds both programs and copies only the perl modules cowsay loads, as perl itself names them.

Still missing: bash (its GPL-3.0 keeps it out of a module linked with the kernel), a network.

Signals anywhere, and thousands of processes, on the lifted Linux 2026-11-27PR #60

Two gaps in the microvm-x64 machine are closed. A program can now take a signal at any point, not only in a system call. And processes that end give back their stacks, so a shell running 500 programs one after another is part of the tests; 4,000 took 5.2 s.

  • Handlers run on top: when the kernel sends a program elsewhere (a signal's handler) on the way back from a fault, an interrupt or a system call, the handler runs above the interrupted code, and the interrupted code goes on when sigreturn comes back to it. A copy-on-write fault that returned with SIGCHLD pending used to stop the machine there.
  • Interrupts in loops are taken on the jump back, at its target: an interrupted loop goes on at its next iteration.
  • Tasks that end (do_task_dead) give back their C stack, their slot and their wasm stack. A new task whose kernel stack had a dead task's stack pointer used to resume the dead one.
  • /init catches a signal sent into a busy shell loop, as on QEMU.

Programs at the same addresses on the lifted Linux 2026-11-27PR #60

The lifted Linux kernel can now run several programs linked at the same addresses. busybox and our own fixtures/linux-hello, both static at 0x400000, run interleaved in /init and print the same 22 lines as on QEMU.

  • lifter --user <name> lifts a program on its own, its functions and tables under its name, with the hash of each page of its code. tools/build-title.sh (PROGRAMS) and pisco build ([lifter] programs) lift each and link them with their list.
  • The machine finds which program runs by its bytes: after a change of CR3 it hashes the code page it is about to run, reading it first as an instruction fetch would, so the kernel maps it. Then it takes the program whose page matches.
  • A machine's code runs the x87 at its full precision, so musl's printf of a double prints what it prints on a CPU.
  • pisco build compiles a cached lift again when the compiler's flags change.

Still missing: bash, whose licence (GPL-3.0) keeps it out of a module linked with the GPL-2.0-only kernel; that needs a module per program.

A disk for the lifted Linux 2026-11-27PR #60

The microvm-x64 machine has a disk: virtio's block device on its MMIO transport. With SW_DISK=16M (zeros) or SW_DISK=<file>, the lifted Linux finds /dev/vda. /init formats it as ext2 with busybox, writes 1,000 lines, mounts it again and reads them back. It worked on its first run.

  • rt/microvm-x64/virtio.c: virtio 1.2's MMIO registers, one queue, reads, writes, flush and the disk's id, interrupts through the IOAPIC's pin 5. The runtime announces the device on the kernel's command line.
  • The kernel gains virtio's MMIO transport, its block driver and ext2. Without a disk, /init still prints what it prints on QEMU.
  • tests/run.sh kernel checks the disk too.

Still missing: the disk's writes are kept in memory, not in its file; there is no network.

A Linux shell to type into, and a Linux image 2026-11-27PR #60

The lifted Linux kernel's console now takes input, so its busybox shell can be typed into: in a terminal (pisco run), in the page (keys as a terminal sends them), or through a pipe. And pisco build recipes/linux makes it an image like any other title's. Two builds with empty caches give the same manifest, and pisco run boots it in Node and in headless Chrome.

  • The 16550 receives: a ring in the module's memory, written by the host and read by the serial port with its receive interrupt. A byte is handed over only while the driver asks for it, because Linux's driver reads the receiver while it probes.
  • Idle waits: when someone types, hlt waits for a key or the next timer on the host's clock; from a pipe the virtual clock stays.
  • A kernel oops fixed: a signal frame written with fxsave into a copy-on-write page reported its fault at address 0, because rt/cpu.h's helpers that reach memory saw a fallback instruction address. They now take the caller's, for every title.
  • pisco build for a machine: [lifter] programs are lifted with the kernel; [run] initrd and cmdline reach the runtime through the image's config.
  • tools/run-chrome.mjs can type (TYPE=<text>). tests/run.sh kernel checks the image, its programs against QEMU, and a typed shell session.

Still missing: disks and a network (virtio), programs at the same addresses as one another, and more than one CPU.

Linux runs its programs 2026-11-27PR #60

The lifted Linux kernel now runs programs: busybox, lifted into the same module, runs the initramfs's /init to its end on the microvm-x64 machine in Node. That covers pipes, a shell in a shell, awk, a 4 MiB file written and hashed, a child killed, a signal handled, ten programs executed. It prints the same 15 lines it prints on QEMU, the same on every run, in 2.5 s from Node's start to the exit port. fork, exec, signals, pipes and files are the kernel's own work, not an imitation of it.

  • lifter --program <elf> (PROGRAMS for tools/build-title.sh) lifts static programs with a kernel, at the addresses the kernel loads them at.
  • A program's longjmp is its own: an indirect jump to a return address enters the code there.
  • About QEMU's speed: with its CPU emulated in software on the same machine, QEMU takes 1.15 s to /init where the lifted kernel takes 0.83 s; awk 0.78 s against 0.86 s; ten execs 16 ms against 18 ms.
  • tests/run.sh kernel checks the programs' output against QEMU's.

Still missing: typing into the console, pisco build of the Linux title, and programs at the same addresses as one another (bash and busybox).

Linux boots, lifted 2026-11-27PR #60

Linux 6.18 runs on PISCO: the whole kernel, lifted ahead of time into one 42 MB module, boots on the microvm-x64 machine in Node to Run /init as init process in 0.9 s, printing the same boot log on every run. No program runs yet: /init is busybox, which is not lifted with the kernel yet; that is next.

  • The code the kernel rewrites while it boots: its runtime constants (the dentry hash table's address and shift, USER_PTR_MAX, listed in runtime_ptr_* and runtime_shift_*) are read from memory, where the kernel wrote them. Its static-call trampolines are decoded as it has rewritten them. Its alternatives stay as the file has them, which is correct on any CPU.
  • Where the kernel goes back into its code: the fix-ups of its exception table, its entry stubs at computed addresses, the byte after an int3 and five bytes on (its self-test emulates a call there). A call may come back on a stack the callee moved on purpose (error_entry), as long as it returns through its own address.
  • The machine grew the boot protocol (the zero page, its memory map, the command line, the initramfs), an MP table, the IOAPIC, the 16550's interrupt, a CMOS clock on the virtual clock's date, SERIALIZE in CPUID, and fxsave, fxrstor and cmpxchg16b in the lifter.
  • tests/run.sh kernel builds the lifted kernel and checks its boot against recipes/linux/traces/boot.txt, twice.

A sixth runtime, a small x86-64 machine 2026-11-27PR #60

The machine Linux will run on, rt/microvm-x64 (base/microvm-x64): one x86-64 CPU in long mode, a software MMU over the kernel's own page tables, a local APIC and its timer, a serial port and an exit port. It is checked on a test kernel of our own, fixtures/microvm-hello. That kernel pages, takes a page fault and returns, has a fault fixed up, handles int3 and ud2, waits for the timer, switches between two tasks, and drops to a ring-3 task that makes system calls until the timer preempts it. Lifted, it prints on its serial port the 20 lines QEMU prints, in Node and in headless Chrome. Linux itself does not run yet; that is next (docs/linux.md).

  • The lifter's machine mode: in a kernel's image (--machine, or any image in the upper half of the address space), the system's instructions are calls of the machine. Every load and store goes through its TLB with the instruction's address, interrupts are taken at each function's start and each jump back, and a call checks that it comes back with the stack it was made with. With it, 56 of Linux's 602,001 instructions are not lifted yet.
  • Faults, interrupts and system calls are nested runs of the kernel's handler: when it returns where it was raised, the lifted function goes on; when it returns elsewhere (a fix-up, a preempted program sent elsewhere), the code there is entered by its address.
  • A host stack for each kernel task: the stack switch in __switch_to_asm suspends one wasm stack and resumes or starts another (JSPI), in web/run-node.mjs and the page's worker.
  • The clock is virtual: it moves a few nanoseconds at each poll and jumps to the next timer when the CPU halts, so a run prints the same every time.
  • tests/run.sh microvm is a default step and runs in CI; it checks QEMU's output too when QEMU is there, and tests/run.sh chrome runs the kernel in the page.

Still missing: Linux's alternatives and static calls, fxsave and xsave, the IOAPIC, the serial port's interrupt and input.

Linux itself as a title, the groundwork 2026-11-27PR #60

The plan to run a real Linux kernel on PISCO: lifted ahead of time like any other title, on a runtime that imitates a small x86-64 machine. Nothing of the kernel runs under PISCO yet. This first step builds the kernel, makes the lifter read it, sets up QEMU as the reference, and measures the three things the design stands on. The reasoning and the numbers are in docs/research/kernel-as-a-title.md; the title's page is docs/linux.md.

  • tools/build-linux.sh fetches Linux 6.18.65 from kernel.org (checked by SHA-256) and builds it with recipes/linux/kernel.config on top of the kernel's tinyconfig: one CPU, no jump labels, no mitigations, no modules, no ACPI, no PCI. It stops at a line the kernel did not take. With busybox (tools/build-busybox.sh, shared with neofetch's build) and recipes/linux/init it packs an initramfs. Two builds give the same files.
  • The lifter reads a kernel (--machine, or any image in the upper half of the address space): 10,853 functions and 583,233 instructions. It does not lift 3,958 of them yet (0.68 %), all instructions of the system: sti, cli, pushfq, wrmsr and about fifty rarer kinds. A kernel's code is taken from its sections, since its executable segment holds its strings too.
  • A fix for every 64-bit title: an operand that is a control, debug or segment register was taken for the general register of the same number (mov cr3, rax wrote RBX). A segment register now reads as its selector in a program; the others are counted as not lifted.
  • QEMU is the oracle (tools/oracle-qemu): it boots the same kernel and initramfs, and what /init's programs print is recorded in recipes/linux/traces/programs.txt (pipes, fork, exec, a file written and hashed, a child killed, a signal handled). tests/run.sh kernel checks it, also on a machine without HPET, PIT and 8259.
  • Three measurements: four JSPI stacks, each with its own C stack, switch in 0.27 µs; a software TLB that a page fault can come back through costs 1.3 to 2.0 times today's lifted code on the benchmark title; and the kernel boots with only a local APIC, an IOAPIC and a serial port.

Still missing: the machine itself (rt/microvm-x64), and so everything that runs. Next is a small test kernel of our own on it, then this one.

The PS5 raymarching tech demo, in the browser 2026-11-27PR #39

ps5-raymarch-techdemo v1.4, a CPU raymarcher built as PS5 homebrew (ten threads, AVX2 and FMA for the console's Zen 2), now runs as a web title on a new base/ps5 runtime. Its three scenes, DualSense and synthesized music work in Node and in headless Chrome. AnyPS5 was the reference for the executable's format and for what the system functions do; nothing of Sony's is used or needed.

  • The lifter reads a native PS5 executable (an ELF of type 0xFE10): its loadable segments, relative relocations (their values kept for the runtime; the file holds 0 there) and imports by NID, named through ps5_nids.txt. The functions start from the entry point and every FDE of .eh_frame_hdr.
  • AVX, AVX2, FMA and BMI are lifted (avx.rs, rt/avx.h) instead of trapping: the demo has about 4,700 such instructions. A ymm register is its xmm register and c->yh[n]. tests/avx.sh checks 120 results of a Zen 2 build against what the CPU printed. A fused multiply-add is a multiply then an add by default (the last bit can differ); OPT='-O2 -DPISCO_FMA_EXACT=1' makes float ones exact but for rare double rounding, about a third slower in the demo. CPUID still does not report AVX, so titles that check it take their SSE paths; a PS5 title does not ask.
  • The runtime (rt/ps5/) answers the 38 system functions this demo calls: libkernel (direct memory, time, pthreads, sysctl), the C library, the system and user services, VideoOut (frame buffers flipped to the GPU back end as a texture), Pad (the page's keys and gamepad as a DualSense) and AudioOut (ports as mixer sources). tools/build-title.sh picks the base for OS=ps5.
  • Headless Chrome now passes --use-vulkan=swiftshader. Without it, Chrome 156 on the machine we used could not create the canvas's 1920x1080 swap chain texture, and the WebGPU device was lost on the first present.
  • tools/build-ps5-raymarch.sh downloads the demo's v1.4 release (GPL-3.0-or-later, not vendored), checks its SHA-256 and builds it. docs/ps5.md says how to run it, what works and what does not.
  • An offline render in Node (SW_CLOCK, SW_DUMP_RAW, SW_AUDIO_WAV, SW_MAX_FRAMES, SW_KEYS) dumps each 1920x1080 frame and the mix for ffmpeg. Worker yields no longer move the virtual clock, so the demo's own timers stay at 60 frames a second.

Still missing: only these 38 functions are there, and an import without a name traps when called; no GPU (AGC) title runs (this one draws on the CPU); pisco build images of a PS5 title are not wired up (tools/build-title.sh is the way); kern.proc.pathname is not answered (the demo prints path=-).
